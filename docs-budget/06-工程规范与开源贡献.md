## 〇、⚠️ 先说一个必须解决的问题：**这个仓库没有 LICENSE**

### 事实

| 检查项 | 结果 |
|---|---|
| 仓库根目录 `LICENSE` / `COPYING` | ❌ **不存在** |
| GitHub API `license` 字段 | ❌ `None` |
| `package.json` 的 `license` 字段 | ❌ 不存在 |
| `package.json` 的 `author` / `repository` | ❌ 都是 `None` |
| README 里的许可声明 | ❌ 全文无 "license / 许可 / 授权 / 版权 / 开源协议" |

### 这意味着什么（请找专业人士确认，我不是律师）

**没有许可证 ≠ 可以随便用。** 按主流著作权法实践：

- 代码默认**保留全部权利**（All rights reserved）
- 严格来说，**没有授权就意味着没有复制、修改、分发的许可**
- 「本地改一改自己用」在实践中风险很低（不涉及分发，且作者公开源码意图明显）
- **但「重新分发修改版」和「对外提供服务」是有实质风险的**
- 我们打算做的「构建自定义镜像 → 部署到自己 NAS」属于**自用**，风险低
- **但如果将来要把这个定制版分享给别人，就必须先拿到授权**

### 已有的善意信号

README 里写了「参与与反馈」：

> - 问题与建议：[GitHub Issues](https://github.com/frankluise5220/MMH/issues)
> - 版本与安装包：[GitHub Releases](https://github.com/frankluise5220/MMH/releases)

说明作者**欢迎反馈**，但这只开了 Issue 的口子，**不等于授权代码使用**。

### 建议动作（开工前）

**在 Issue 里问作者两件事**（这是最稳妥、也最符合礼仪的做法）：

1. **能否补一个开源许可证？**（如 MIT / Apache-2.0 / AGPL-3.0）
   - 说明：没许可证会让想贡献的人**无法合法提交 PR**
   - 对作者也有利：明确授权才能形成社区
2. **是否接受外部 PR？** 如果接受，希望遵循什么流程

> **我们的场景下，不发这个 Issue 也能自用**（本地改、自己部署）。
> 但**要往上游提 PR，就绕不开许可问题** ——
> 你贡献的代码会与他的代码合并、再被分发，没有许可证这链条不完整。

## 一、与上游更新共存的方案

### 1.1 仓库现状

```
当前 clone：git clone --depth 1（浅克隆，只有 1 个提交 75417fb）
remote：    origin → https://github.com/frankluise5220/MMH.git
分支：      main
```

**⚠️ 浅克隆的问题**：`--depth 1` 拿不到历史，`git fetch upstream` 后**无法正常 rebase**。
**第一步必须 deepen**：

```bash
cd /Volumes/VibeCoding/01-投资/MMH
git fetch --unshallow origin        # 补全历史
```

### 1.2 推荐的分支模型：**upstream main + 长期定制分支**

```
main                    ← 与 upstream/main 保持一致（不提交任何定制代码）
  │
  └── feat/budget-calendar   ← 我们的定制与功能，长期存在
        │
        └── feat/transaction-heatmap   ← 每个功能一个短分支，合回上面
```

**规则**：
- `main` **永远干净**，只用于 `git pull upstream main`
- 所有定制在 `feat/*` 或 `local/*` 分支
- 每个功能**单独开短分支**，做完合回长期分支 —— 这样将来能**按功能拆 PR**

### 1.3 日常同步流程

**一次性设置**：

```bash
cd /Volumes/VibeCoding/01-投资/MMH
git fetch --unshallow origin
git remote add upstream https://github.com/frankluise5220/MMH.git
git remote set-url --push upstream DISABLE     # 防止误推到上游
git fetch upstream
```

**每次上游更新后**：

```bash
git fetch upstream
git checkout main && git merge --ff-only upstream/main    # main 只快进
git checkout feat/budget-calendar
git rebase main                                            # 把定制挪到新基线
# 解决冲突后
git push --force-with-lease origin feat/budget-calendar
```

> **用 `rebase` 还是 `merge`？**
> - `rebase`：历史线性、干净，但每次冲突都要逐个提交解决
> - `merge`：一次解决全部冲突，但历史里全是合并节点
>
> **建议：定制分支用 `rebase`，且频繁做**（每次上游更新就 rebase）。
> 冲突越早解决越便宜；攒三个月再 rebase 会很痛苦。
>
> ⚠️ **但注意**：如果要给上游提 PR，**PR 分支绝不能用 rebase 后的 force-push**
> 覆盖已经 review 的提交（会打乱 review 记录）。PR 分支用 `merge`。

### 1.4 冲突最小化策略（**最重要，直接决定维护成本**）

| 策略 | 做法 | 效果 |
|---|---|---|
| **① 优先新增文件** | 新组件/新 API 用**新文件**，不改现有 | 几乎零冲突 |
| **② 改文件时"整块独立"** | 必要改动集中成一整块，配显著注释 | 冲突点少且好解 |
| **③ 改动加标记** | 所有我们的改动加同一前缀注释，如 `// [MMH-BUDGET]` | `grep -r "MMH-BUDGET"` 一键定位全部改动 |
| **④ 新 API 用新路由** | 不动既有 route.ts，新开 `/api/v1/budgets/` | 零冲突 |
| **⑤ i18n 集中追加** | 中英文词条加在我们自己的注释块里、集中一段 | 与作者新增词条易合并 |

#### 具体到本次预算功能

| 要改的既有文件 | 改动量 | 冲突风险 | 缓解办法 |
|---|---|---|---|
| `prisma/schema.prisma` | 加 2 个模型 + 2 行反向关系 | **中** | 模型**追加到文件末尾**；反向关系加在我们模型旁边并注释 |
| `src/lib/server/system-tasks.ts` | 加一段 try/catch | 中 | 集中成一个函数调用，配 `[MMH-BUDGET]` 注释 |
| `src/lib/i18n-core.ts` | 中英文各加词条 | **高**（作者常改）| 集中追加 + 注释块 |
| `src/components/layout/SidebarClient.tsx` | 加导航项 | **高** | **见下方替代方案** |

#### 侧边栏的高冲突替代方案

`SidebarClient.tsx` 是两个大分支里硬编码的（折叠态 ~1263、展开态 ~1389），
而作者**频繁改这里**。两个选择：

- **方案 A（改 Sidebar）**：加导航项。冲突风险高，但入口显眼
- **方案 B（不改 Sidebar）**：把预算/日历做成 **overview 页里的卡片**，
  或 **`/reports` 的一个视图** —— 用户已说「先完善 MMH 概览页」，
  **这正好与 B 一致，冲突为零** ✅

> **建议走 B**：既符合用户「先完善概览页」的指示，又把冲突风险降到零。

### 1.5 版本与镜像的对应关系

```
upstream v0.1.71  →  我们的分支基于它  →  镜像打标签 0.1.71-budget.1
upstream v0.1.72  →  rebase  →  镜像 0.1.72-budget.1
```

**镜像 tag 里带 upstream 版本号**，这样 NAS 上跑的是哪个上游版本一目了然。

## 二、向开源社区提交贡献的方案

### 2.1 现状（对贡献的影响）

| 检查项 | 结果 | 影响 |
|---|---|---|
| `CONTRIBUTING.md` | ❌ 无 | 没有明文流程，需先问作者 |
| `.github/ISSUE_TEMPLATE/` | ❌ 无 | 提 Issue 用自由格式 |
| **CI 是否在 PR 上跑** | ❌ **所有 workflow 的 on 都是 `push` / `release` / `workflow_dispatch`，没有任何 `pull_request`** | **PR 不会被自动校验** → 必须自己跑校验 |
| 提交信息风格 | Conventional Commits（如 `chore(fnos): …`、`fix(login): …`、`docs(release): …`）| 我们照此风格 |
| Fork 数 | 2 | 社区规模小，PR 大概率会被认真看 |

### 2.2 贡献流程（建议）

```
Step 0  先提 Issue 问两件事
        · 能否补 LICENSE（见第〇节）
        · 是否接受这个功能的 PR / 有无偏好做法
        ← 别直接写代码再提 PR，容易被拒或要求大改

Step 1  Fork 到自己的 GitHub 账号，建 feature 分支（基于最新 main）

Step 2  开发，遵守项目约定（见 2.3）

Step 3  本地跑全部校验（CI 不管 PR，得自己跑）

Step 4  提交 PR
        · 标题用 Conventional Commits
        · 描述里写清：解决什么问题、怎么实现、怎么验证、有无破坏性变更
        · 一次 PR 只做一件事

Step 5  按 review 意见改（用 merge，不要 force-push 覆盖已审提交）
```

### 2.3 必须遵守的项目约定

| 约定 | 要求 | 来源 |
|---|---|---|
| **提交信息** | Conventional Commits：`feat(budget): …` / `fix(...)` / `docs(...)` | 实测 git log |
| **i18n** | 新增文案**必须同时加中/英/日**（项目支持三语）| README 技术栈节 |
| **双 schema** | 改 `schema.prisma` 后必须跑 `node scripts/generate-native-sqlite-schema.cjs` | 脚本注释 |
| **迁移** | 必须配套 `prisma/migrations/`，且过 `npm run check:migration-coverage` | package.json scripts |
| **代码风格** | `npm run lint`（ESLint 已配置 `eslint.config.mjs`）| 仓库 |
| **多端一致** | 「多端共享同一套业务口径」—— 改口径要考虑桌面/Android | README 技术栈节 |
| **备份完整性** | `npm run check:backup` | package.json |

### 2.4 提交前要跑的校验清单

CI 不在 PR 上跑，所以**这些必须本地全过**：

```bash
npm run lint                      # ESLint
npm run check:migration-coverage  # 迁移是否覆盖 schema 变更
npm run check:backup              # 备份完整性
node scripts/generate-native-sqlite-schema.cjs   # 同步 SQLite schema
# 以及项目自带的其它 check:*（见 package.json）
```

> ⚠️ 注意：**部分 `check:*` 脚本用了 `tsx`**，需要 devDependencies 装齐。

### 2.5 哪些功能适合提 PR

| 类型 | 适合提 PR | 原因 |
|---|---|---|
| **通用能力**（交易日历、热力图、预算警告）| ✅ **很适合** | 任何用户都用得上，与作者的产品方向一致 |
| 你的个人偏好（特定的豁免类目、个人分类约定）| ❌ 不提 | 属于个人配置，不该进上游 |
| 与 MMH 现有设计冲突的改动 | ❌ 不提 | 会被拒 |

**建议拆分**（一次 PR 一个）：
```
PR #1  feat(budget): 交易热力图（纯新增，无 schema 改动）
PR #2  feat(budget): 交易日历（纯新增）
PR #3  feat(budget): 今天/本周/今年 汇总卡（纯新增）
PR #4  feat(budget): 预算模型 + API + 页面（含 schema 迁移）
```
**前三个无 schema 改动、纯新增文件 → 被接受概率最高，也最安全。**

### 2.6 一句话总结贡献策略

> **先问许可与意愿 → 功能拆小 → 优先纯新增 → 遵守约定 → 本地跑全校验 → 一个 PR 一件事。**

## 三、本地环境：对齐 Docker（用户指示）

### 3.1 现状

```
本机：macOS · Node v24.18.0
Docker：❌ 未安装
Postgres：❌ 未安装
```

用户指示：**本机直接安装 Docker / Postgres，对齐 Docker 环境**。

### 3.2 为什么对齐 Docker 是对的

| 项 | 生产（NAS）| 本机现状 | 对齐后 |
|---|---|---|---|
| 数据库 | **PostgreSQL 15** | 无 | PostgreSQL 15 |
| 运行时 | Node **20**（Dockerfile `node:20-bookworm`）| Node **24** | Node 20 容器 |
| 部署方式 | Docker Compose | 无 | Docker Compose |
| 构建 | Dockerfile 多阶段 | — | 同 |

**关键理由**：
- MMH 有**两套 schema**（Postgres / SQLite）。用 SQLite 开发会**掩盖 Postgres 特有问题**
  （索引行为、并发、事务、Decimal 精度）
- 生产是 Postgres → **本地就该是 Postgres**，否则「本地通过、线上炸」
- 用 Docker Compose 起，**与 NAS 的 `deploy/nas/docker-compose.yml` 几乎一致**

### 3.3 建议路径

**用仓库自带的 compose**（`docker-compose.yml` 是「本仓库内开发与调试用」，
注释明确写了 Postgres 只绑 `127.0.0.1:5433`）：

```bash
cd /Volumes/VibeCoding/01-投资/MMH
cp .env.example .env         # 按需改 POSTGRES_PASSWORD 等
docker compose up -d postgres   # 先只起数据库
# 或全起（含 app 镜像）
docker compose up -d
```

**Docker 方案选择**（macOS 上要装）：

| 方案 | 说明 | 建议 |
|---|---|---|
| **Docker Desktop** | 官方，最省事，含 compose | ✅ 推荐（个人使用免费）|
| Colima + docker CLI | 开源、轻量，需额外装 CLI | 备选 |
| OrbStack | 更快更省电，商业授权 | 备选 |

> ⚠️ **本机安装 Docker Desktop 需要管理员权限与 GUI 操作，我无法代做。**
> 你在「应用程序」里装好、启动一次即可；之后 `docker` 命令我就能用。

### 3.4 环境就绪的判定标准

```bash
docker --version                 # 有输出
docker compose version           # 有输出
cd /Volumes/VibeCoding/01-投资/MMH && docker compose up -d postgres
docker compose ps                # mmh-db 状态 healthy
psql "postgresql://mmh-fs:...@127.0.0.1:5433/mmh" -c '\dt'   # 能连上
```
