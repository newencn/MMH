>
> 目标仓库：`/Volumes/VibeCoding/01-投资/MMH`（v0.1.71，commit 75417fb）

## 一、背景与问题

### 1.1 为什么要做这个

用户的家庭记账现状是**三家并行**，各自解决了不同问题，但**都没有预算能力**：

| 系统 | 定位 | 现状 |
|---|---|---|
| **MMH** | 家庭唯一账本（自建，NAS 部署） | 1346 笔流水、80 个数据模型、投资/信用卡/贷款齐全。**没有任何预算模型** |
| **HomeLedger** | 新装的第二账本，用于对比 | 有 budgets 视图，但能力未验证；开放 API 只有 5 个端点 |
| **ezBookkeeping** | 用户试用过的开源记账（Go+Vue，5748★）| **无预算分配**，但有零配置的**月度支出进度 + 月末预测** |
| **飞书多维表格** | 曾考虑的展示层 | 无统计聚合接口，做面板要自己算，**已评估不合适** |

**核心痛点**：用户**不知道自己这个月花超了没有**。

现有系统只能"事后看统计"（MMH 的 `/statistics` 给出类目占比），
但**没有"事前设限额 + 事中预警"的能力**。

### 1.2 为什么要在 MMH 里做，而不是别处

用户明确提出「MMH 去修改页面、新增功能如预算警告」。

关键判断依据（实测）：

- **MMH 有 80 个数据模型，但没有 Budget 模型** → 加预算必须**改 schema**
- 改 schema 是 DSH 面板层或任何外部系统**做不到的**（外部只能调 API，不能加数据模型）
- 这正是 fork MMH 源码的**正当理由** —— 符合此前评估的结论：
  > "什么时候才值得 fork：当你想改的东西涉及**数据模型**时。"

### 1.3 数据现状（影响设计的事实）

来自 2026-10-11 的实测统计：

```
支出 1230 笔  ¥868,162   （已分类 820 笔 / ¥676,174，按金额 77.9%）
收入 116 笔   ¥857,701   （已分类 99 笔 / ¥841,983，按金额 98.2%）

支出 Top 类目：
  贷款本金   ¥310,653 (35.8%)   ← 房贷/个贷
  信用借还   ¥128,842 (14.8%)   ← 信用卡还款
  房贷       ¥97,525  (11.2%)
  房租       ¥38,492  (4.4%)
  信用卡还款  ¥23,906  (2.8%)
  餐饮美食   ¥18,022  (2.1%)
```

**这张表直接决定了预算功能的设计难点**：

1. **大额刚性支出占 51%**（房贷+房租+贷款本金）
   → 这些**不该被当成"超支"来警告**，它们金额固定、每月必然发生。
   → 预算必须能**标记豁免类目**，否则每月都会被"超支"淹没。

2. **`信用借还` / `信用卡还款` 不是消费**
   → 是资金流转。若纳入预算会把账算重。
   → 预算统计必须**排除内部流转类目**（与 MMH 现有 `isCreditCardRepaymentTransfer`
     等语义判断保持一致）。

3. **类目覆盖率只有 77.9%（按金额）**
   → 有 22% 的钱没有类目。若预算只按类目算，会有盲区。
   → 需要**「未分类」也是一个可预算/可查看的桶**，否则用户会误以为没超。

## 一点四、用户的实施指示（2026-10-11，最新）

用户看过两家截图后给出明确指示：

> 1. **在 MMH 补充交易热力图、交易日历**
> 2. **四张卡：今天 / 本周 / 本月 / 今年，各显示收入+支出 + 底部时间范围**
> 3. **设计规范保持 MMH 现有的**

### 由指示确定的三件事

**① 这两个组件是"可视化先行"，不强依赖预算功能**

用户把它们单独列出来，说明**即使预算还没做，这两个组件本身就有价值**。
技术上它们只需要**按日聚合的收支数据**（MMH 现在没有，但很容易加），
**不依赖 `Budget` / `BudgetAlert` 两个新模型**。

→ **可以独立于预算先交付**，风险更低、见效更快。

**② 四张时间卡需要新增三个时间边界**

MMH 现在只有"本月"（`monthIncome` / `monthExpense`）。
要新增：**今天 / 本周 / 今年**。日期工具已有
（`startOfDayUtc` / `addDaysUtc` / `addCalendarYearsUtc`），缺的是聚合查询。

**③ 设计一律沿用 MMH 现有规范**

详见 [05-界面设计规范.md](./05-界面设计规范.md) §3.3 ——
只用 `.panel-surface` / `.panel-header` / `MetricCard` / `CashFlowCard` /
`directionalClass()` / 现有 CSS 变量，**不引入第二套设计语言、不硬编码颜色**。

### 交付顺序（据此调整）

```
第 1 批（无依赖，可先做）
  · 按日聚合查询（日历与热力图共用）
  · 交易热力图
  · 交易日历
  · 今天/本周/本月/今年 四张卡

第 2 批（预算本体）
  · Budget / BudgetAlert 模型 + 迁移
  · 预算页（设额度、进度条、三级配色）
  · 超支警告 + 系统任务

第 3 批（融合）
  · 交易日历上叠加"当日预算剩余"
  · 热力图色深可切"预算消耗比"
```

## 一点五、设计方向（用户试用三家后的反馈，2026-10-11）

用户实际试用过 Firefly III、Actual Budget、ezBookkeeping 三家，反馈如下：

| 产品 | 用户实际评价 | 结论 |
|---|---|---|
| **Firefly III** | 「太 OLD 了」 | ❌ 直接出局 |
| **Actual Budget** | 「**首页面板数据呈现不错**，但其他交互也 OLD 了」 | ⚠️ 抄它的面板，不抄交互 |
| **ezBookkeeping** | 「**首页交易日历和热力图增加预算就更好了**」 | ✅ 抄它的可视化，**并叠加预算** |

> 用户提供了两个界面的**真实截图**，我已据此产出
> **[05-界面设计规范.md](./05-界面设计规范.md)**（逐块拆解布局、组件、配色、信息层级）。

### 由此推出的三条设计要求

**① 交互必须现代，不能"OLD"**
Firefly III 和 Actual Budget 都被评为"OLD" —— 说明**交互与视觉的现代感是硬指标**，
不是锦上添花。目标水准：ezBookkeeping 的界面（Material Design 3 风格）。
MMH 现有界面需对齐这个水准，至少新增的预算页不能拖后腿。

**② 具体的可视化清单（用户明确点名）**

| 组件 | 用户态度 | 来源参考 |
|---|---|---|
| **交易日历**（月历，每日显示收支金额）| ✅ **明确想要** | ezBookkeeping 首页右侧 |
| **交易热力图**（按周×日期的深浅格子）| ✅ **明确想要** | ezBookkeeping 首页左上 |
| **面板式 KPI 卡片** | ✅ 「数据呈现不错」 | Actual Budget 首页 |
| **在日历/热力图上叠加预算** | ✅ 「增加预算就更好了」 | **我们的创新点** |

**③ 用户看到的两个参考界面（截图要点）**

**ezBookkeeping 首页**（用户截图）：
```
左上：交易日历热力图（日×星期 的深浅网格，颜色深浅=当日金额）
右上：交易日历（月历，每格显示当日收入/支出，如 $6,000.00 / $15.50）
    高价日/大额日有背景色高亮
左中：支出分类排行（进度条 + 金额 + 占比%，如 Housing 47.03%）
中：  支出趋势（面积图）
下：  今天 / 本周 / 本月 / 今年 四张汇总卡（收入 / 支出）
```

**Actual Budget 首页**（用户截图）：
```
顶部：Total Income (YTD) / Total Expenses (YTD) / Avg Per Month / Avg Per Transaction
      —— 四个大数字 KPI 卡
中部：Net Worth 走势 · Cash Flow 柱状 · This Month 对比 · Budget Overview 对比
     · 3-Month Average 对比（虚线=基准，实线=当期）
下部：Transaction Calendar（月历，每日柱状显示收/支）
     · Recent Net Worth Change（大数字）
左侧栏：All accounts / On budget / Bank of America … / Off budget
     **+ 底部「Add account」**
```

### 对我们的具体启示

1. **「本月 vs 上月」对比要显式做出来** —— Actual 的 `This Month` / `Budget Overview`
   / `3-Month Average` 三张卡都是**当期 vs 基准**的对比图。这类对比比绝对值更有信息量。
2. **交易热力图是"零成本高感知"的组件** —— 实现简单（按日聚合），
   但视觉冲击强。**应优先做**。
3. **交易日历可以让预算"落到每一天"** —— 这正是用户的诉求
   （「交易日历和热力图增加预算就更好了」）：
   在月历的每日格子里，除了当日收支，还可以显示
   **「当日可用额度」**（月度额度 ÷ 剩余天数）或**累计预算消耗进度**。
   → 这一条把 D5（每日可用额度）从"P2 可选"提升为**值得认真设计**。
4. **KPI 大数字卡片** —— Actual 顶部四张卡的做法（大字号 + 小标签 + 时间范围）
   比 MMH 现在的纯文字更易读。

### 需要升级的需求项

| 原编号 | 原优先级 | **新优先级** | 理由 |
|---|---|---|---|
| F2 总预算 | P0 | P0（不变）| 已确认 |
| — | — | **P1 新增：交易热力图** | 用户明确想要，实现简单 |
| — | — | **P1 新增：交易日历（月历，每日收支）** | 用户明确想要 |
| — | — | **P1 新增：月度进度 + 预计月末支出** | 抄 ezBookkeeping，零配置有用 |
| F14 每日可用额度 | P2 | **P1 提升** | 与交易日历结合是用户点名的创新点 |
| — | — | **P1 新增：本月 vs 上月对比卡** | 抄 Actual，比绝对值有信息量 |

## 二、竞品对比

### 2.1 成熟产品怎么做预算提醒

**MX（美国主流金融科技方案商，其 Budgets Widget 被大量银行 App 采用）**
参考：[Budgets Widget - MX Documentation](https://docs.mx.com/products/experience/pfm/widget-overviews/budgets-widget)

关键设计（**值得直接借鉴**）：

- **三级健康度配色**：
  ```
  绿色  = 用量 < 80%
  黄色  = 80% ~ 100%
  红色  = 超过 100%
  ```
- **自动生成预算**：按各品类**过去两个月的平均支出**生成初始额度
  （前提：交易数据完整、类目准确）
- **两级预算结构**：主预算 + 子预算；子预算调高会自动抬高主预算
- **可视化以"气泡"呈现**：气泡**大小**=占收入比例，**颜色**=是否超支
  → 一眼看出"哪类花得多 + 哪类有危险"

**YNAB / MoneyWiz（个人记账工具）**
参考：[MoneyWiz vs. YNAB Comparison Chart](https://sourceforge.net/software/compare/MoneyWiz-vs-YNAB/)

- YNAB 是**零基预算**（每一分钱都要预先分配），理念重、上手陡
- MoneyWiz 更接近**类目额度 + 进度条**，与 MX 类似
- 两者共同点：**预算必须绑定类目**，且**支持结转**（上月没用完的额度带到下月）

**国内记账 App（随手记 / 有米记账 等）**
参考：[有米记账 App Store 页](https://apps.apple.com/bg/app/%E6%9C%89%E7%B1%B3%E8%AE%B0%E8%B4%A6-%E6%9E%81%E7%AE%80%E8%AE%B0%E8%B4%A6%E8%BD%AF%E4%BB%B6%E8%B4%A2%E5%8A%A1%E7%AE%A1%E5%AE%B6/id1587461748)

- 普遍是**月度类目预算 + 阈值提醒**（70%/90%/100% 之类）
- 部分支持**每日可用额度**（月度额度 ÷ 剩余天数）——对控制节奏很有用

### 2.2 三家系统的预算能力对比

| 能力 | **MMH**（现状） | **HomeLedger** | **飞书多维表格** | 主流记账 App |
|---|---|---|---|---|
| 数据模型有预算 | ❌ **无** | ⚠️ 有 budgets 视图 | ⚠️ 要自己建表 | ✅ |
| 类目预算 | ❌ | ⚠️ 未验证 | ✅ 可建 | ✅ |
| **总预算** | ❌ | ⚠️ 未验证 | ✅ 可建 | ✅ |
| **超支警告** | ❌ | ⚠️ 未验证 | ❌ 无通知机制 | ✅ |
| 阈值分级（80/100/120%） | ❌ | ⚠️ | ❌ | ✅ |
| 自动生成预算建议 | ❌ | ❌ | ❌ | ⚠️ 部分有 |
| 豁免类目（房贷等不参与） | ❌ | ⚠️ | ❌ | ⚠️ 少见 |
| 排除内部流转（还款/转账） | ⚠️ 统计里有语义判断，但预算无 | ⚠️ | ❌ | ⚠️ |
| 每日可用额度 | ❌ | ❌ | ❌ | ⚠️ 部分有 |
| 结转（上月余额带下月） | ❌ | ❌ | ❌ | ⚠️ 部分有 |
| 提醒渠道 | 邮件模块可用 | 未验证 | 飞书通知 | App 推送 |
| 现有历史数据 | **1346 笔（最大优势）** | 少量 | — | — |

**结论**：

- **MMH 的唯一短板就是"没有预算"**，而其他能力（资产、投资、信用卡账单、
  分类语义、邮件）它最全 → **在 MMH 里补预算的边际收益最大**
- **飞书方案已排除**：无通知机制、要自己算、且会变成第三份数据副本
- **HomeLedger 的 budgets 视图值得参考**，但它的开放 API 读不到全量（硬上限 50 条），
  不适合做预算计算的数据源
- **值得抄的设计**：① 80/100 两级阈值配色 ② 按历史均值自动生成额度
  ③ 气泡/进度条可视化 ④ 每日可用额度（这个国内 App 的巧思 MMH 可以做得更好）

## 三、需求描述

### 3.1 用户故事

> 作为家庭账本的维护者，我希望**给某些类目设月度额度**，
> 并在**接近或超过额度时被提醒**，这样我能及时发现异常消费、调整后半月支出。

> 我**不希望**每月都被"房贷超支"这种必然性支出打扰。

### 3.2 功能需求（分优先级）

**P0 — 必须有的（MVP）**

| 编号 | 需求 | 说明 |
|---|---|---|
| F1 | 设置类目月度预算 | 每个类目一个额度，可启用/停用 |
| F2 | 设置总预算 | 不含豁免类目的总限额 |
| F3 | 预算进度展示 | 已花/额度 + 百分比 + 剩余 |
| F4 | 三级状态配色 | 绿 <80% · 黄 80–100% · 红 >100% |
| F5 | 超支警告 | 跨过阈值时产生一条警告记录 |
| F6 | **豁免类目** | 房贷/房租/贷款本金等可标记为不计入预算 |
| F7 | **排除内部流转** | 信用卡还款、信用借还、转账不计入预算支出 |

**P1 — 应该有的（含用户点名的可视化）**

| 编号 | 需求 | 说明 | 来源 |
|---|---|---|---|
| F8 | 阈值可配 | 默认 80%，可改（如 70/90） | — |
| F9 | 警告去重 | 同一预算 + 同一周期 + 同一级别只提醒一次 | — |
| F10 | 页面内横幅提醒 | 进 MMH 就能看到哪些超了 | 决策 D3 |
| F11 | 未分类桶 | 「未分类」也作为一个可查看/可预算的项 | 数据现实 |
| F12 | 历史月份查看 | 能回看往月预算执行情况 | — |
| **F18** | **交易热力图** | 按「日 × 星期」的深浅网格，颜色深浅=当日金额 | **用户点名**（ezBk）|
| **F19** | **交易日历** | 月历视图，每格显示当日收入/支出，大额日高亮 | **用户点名**（ezBk）|
| **F20** | **月度进度 + 预计月末支出** | 已过 X% 进度条 + 按当前速度外推的月末金额 | ezBk 零配置设计 |
| **F21** | **每日可用额度** | 剩余额度 ÷ 剩余天数，**并落在交易日历的每日格子里** | **用户点名的创新点** |
| **F22** | **本月 vs 上月对比卡** | KPI 卡显示当期与基准的对比（Actual 的做法）| 用户体验反馈 |

**P2 — 可以后做的**

| 编号 | 需求 | 说明 |
|---|---|---|
| F13 | 按历史自动生成额度 | 取过去 2 个月该类目均值（学 MX） |
| F23 | 预算消耗热力图 | 把**预算**而非金额作为热力图的色深维度 |
| F15 | 邮件/定时汇总 | 复用 MMH 已有 SMTP 配置 |
| F16 | 结转 | 上月未用完额度带入下月（**Firefly III 此处有已知 bug，谨慎**）|
| F17 | 子预算层级 | 主类目下细分（如 餐饮 → 午餐/外卖） |

> **F14（每日可用额度）已从 P2 提升为 F21（P1）** ——
> 因为用户明确提出「交易日历和热力图增加预算」，
> 而「每日可用额度」正是把预算落到日历上的最自然形式。

**P0/P1 的划分依据**：P0 保证"预算能用"（设额度 + 看进度 + 被提醒），
P1 保证"用户愿意用"（可视化 + 现代交互）。
用户的反馈表明**第二类不是可选项**。

### 3.3 非功能需求

| 项 | 要求 |
|---|---|
| **数据安全** | 改动不得破坏现有 1346 笔数据；上线前必须备份；迁移必须可回滚 |
| **兼容性** | 同时支持 Postgres（生产）与 SQLite（Windows 桌面版）；两个 schema 要同步 |
| **性能** | 预算计算不得拖慢记账写入；聚合查询要有索引 |
| **多租户** | 所有预算数据必须带 `householdId`，不能串户 |
| **不阻塞记账** | 预算检查失败**不能**导致记账失败（警告逻辑旁路，失败只记日志） |
| **视觉与交互水准** | 用户明确评价 Firefly III / Actual「OLD」。新增页面必须达到 ezBookkeeping 的现代水准（Material 风格），并以 MMH 现有主题变量实现，不引入第二套设计语言 |
| **性能（热力图）** | 热力图/日历是聚合查询，必须走索引，不得全表扫描；跨月查看要分页或限制范围 |

## 四、方案设计（初稿，待评审）

### 4.1 数据模型（草案）

```prisma
/// 月度预算
model Budget {
  id          String   @id @default(cuid())
  householdId String
  categoryId  String?          // null = 总预算
  amount      Decimal  @db.Decimal(18, 2)
  period      String   @default("monthly")
  alertPct    Int      @default(80)      // 预警阈值
  enabled     Boolean  @default(true)
  exempt      Boolean  @default(false)   // 豁免类目（不计入总预算）
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  Household   Household @relation(fields: [householdId], references: [id], onDelete: Cascade)
  Category    Category? @relation(fields: [categoryId], references: [id], onDelete: Cascade)

  @@unique([householdId, categoryId])
  @@index([householdId, enabled])
}

/// 超支警告记录（去重用）
model BudgetAlert {
  id         String   @id @default(cuid())
  budgetId   String
  periodKey  String            // "2026-10"
  level      Int               // 80 / 100

  notifiedAt DateTime @default(now())
  readAt     DateTime?

  Budget     Budget @relation(fields: [budgetId], references: [id], onDelete: Cascade)

  @@unique([budgetId, periodKey, level])   // 同一周期同一级别只提醒一次
  @@index([periodKey])
}
```

### 4.2 警告逻辑（草案）

```
计算"本月已花"：
  取该类目下 [月初, 月末) 的支出合计
  ├ 排除 type=transfer / investment
  ├ 排除内部流转类目（信用卡还款、信用借还）
  └ 排除 exempt=true 的类目（仅在算总预算时）

判断级别：
  ratio = spent / amount
  ratio >= 100% → level 100
  ratio >= alertPct(默认80%) → level alertPct

写警告：
  若 (budgetId, periodKey, level) 已存在 → 跳过（去重）
  否则插入 BudgetAlert

触发时机（两条）：
  ① 记账后即时检查 —— 记账流程末尾旁路调用，失败不影响记账
  ② 每日定时扫描 —— 兜底（防止漏检查）
```

## 五、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **schema 迁移破坏生产数据** | 账本损坏 | ①本地先跑通 ②上线前完整备份 ③迁移可回滚 ④先在副本库演练 |
| SQLite / Postgres 两套 schema 不同步 | Windows 桌面版挂 | 改完 `schema.prisma` 后必须同步生成 native schema |
| 迁移覆盖率检查失败 | CI/校验不过 | 项目有 `check:migration-coverage`，要配套写迁移 |
| 上游更新导致分叉 | 合并冲突 | 尽量**新增文件**、少改现有文件；把改动集中在独立模块 |
| 预算逻辑算错（把还款算成消费） | 误导用户 | 复用 MMH 现有语义判断函数，不自己发明 |
| 大额刚性支出淹没警告 | 功能失效 | **豁免类目是 P0**，不是可选项 |
| 未分类占比 22% | 预算有盲区 | 提供「未分类」桶并显式提示 |

## 六、待你确认的决策点

以下 5 项会直接影响实现，**需要你拍板**：

### D1. 预算粒度
- (a) 只要类目预算
- (b) 类目 + 总预算
- (c) 再加账户维度（如"微信零钱每月不超过 X"）
- (d) 再加收入/储蓄目标

### D2. 豁免类目的默认集合
我建议默认豁免这几个（金额大且刚性）：
```
贷款本金 · 房贷 · 房租 · 信用借还 · 信用卡还款
```
**你要不要调整？**（比如房贷其实想监控？）

### D3. 提醒方式
- (a) 页面内横幅/高亮（零依赖，最可靠）
- (b) 邮件（复用 MMH 已有 SMTP）
- (c) 写到 DSH 面板（我们的插件读 MMH 预算状态）
- (d) 以上多选

### D4. 阈值分级
- (a) 两级：80% 预警 / 100% 超支（学 MX）
- (b) 三级：80% / 100% / 120%（多一档"严重超支"）
- (c) 可自定义每级

### D5. 是否要「每日可用额度」
`剩余额度 ÷ 剩余天数` —— 国内 App 的巧思，对控制节奏很有用，但增加复杂度。
