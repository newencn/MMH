## 〇、用户的原始反馈

> 「快速使用过 Firefly III **太 OLD 了**。Actual 的**首页面板数据呈现不错**，
> 但**其他交互也 OLD 了**。ezbookkeeping 的**首页交易日历和热力图增加预算就更好了**。」

**三条可执行的设计要求**：

1. **交互必须现代** —— Firefly III 与 Actual 都被评为 OLD，说明这是硬指标
2. **面板式数据呈现** —— Actual 的首页做法要学
3. **交易日历 + 热力图是核心组件**，且要**叠加预算信息**（我们的差异化）

### 1.2 交易日历（**用户点名的组件 #1**）

从截图提取的规格：

| 项 | 规格 |
|---|---|
| 表头 | 周日 / 周一 / 周二 / 周三 / 周四 / 周五 / 周六 |
| 格子内容 | **日期数字**（左上）+ **收入**（红/橙色，$6,000.00）+ **支出**（灰/黑色，$15.50）|
| 空日期 | 只显示灰色日期数字，如 15 / 29 / 30 / 31 |
| **高亮** | 大额/多笔的日期有**浅色背景块**（截图里 11 号是浅粉底，1 号是浅粉底，22/23/28 号有浅粉底）|
| 特殊 | 28 号出现**两行支出**（$200.00 和 $160.00）→ 说明一格内可堆叠多笔 |
| 货币符号 | 带 `$` 前缀，两位小数 |
| 收入颜色 | 偏红/橙（截图 1 号 `$6,000.00` 是红色）|
| 支出颜色 | 偏灰/黑（`$15.50`、`$1,075.30` 是深灰）|

### 1.3 交易热力图（**用户点名的组件 #2**）

| 项 | 规格 |
|---|---|
| 布局 | **行 = 星期日~六**（7 行），**列 = 周**（横向铺开，截图可见约 30+ 列）|
| 格子 | 小方块，**无边框**，有间距 |
| 颜色 | **橙色系单色深浅**（品牌色 `#C87941` 左右的深浅档）|
| 空白 | 无交易的日期是**极浅的米色/灰白**（近底色）|
| 数据密度 | 截图里只有最近几周有深色格 → **说明它按时间推进填充，历史空白** |

> ⚠️ 注意截图里热力图**几乎整片是空的**，只有最右侧几格有颜色。
> 这是因为它按「日×周」铺一整年，而 demo 数据只覆盖几天。
> **我们做的时候要考虑**：空数据时是否收缩范围（只显示有数据的月份），
> 避免出现"一大片空白"的观感。

### 1.4 其他可借鉴细节

- **支出分类排行**：横向进度条 + 金额右对齐 + 占比百分比，**条形颜色每类不同**（黑/青/橙）
- **四张时间卡**（今天/本周/本月/今年）：每张显示**收入**与**支出**两行，
  底部小字给**时间范围**（如 `10月1日 – 10月31日`）
- **主色**：暖橙/赭色系（`#C87941` 一类），配大量留白

### 2.2 可借鉴的具体做法（**用户说"数据呈现不错"**）

**① 超大字号 KPI 卡**
```
标签：Total Income (YTD)      ← 小字，灰色
时间：1月 2026 - 10月 2026     ← 更小，浅灰
数值：15,766.31               ← 超大号，占卡片主体
颜色：收入绿 / 支出红
```
> 四张卡并排，**信息层级是"数值 >> 标签 > 时间范围"**。

**② 当期 vs 基准的对比图（最有价值的模式）**
三张卡都是同一个模式：
```
标题：This Month
副标题：Compare 10月 2026 to 9月 2026      ← 明确写出对比口径
右上角：-158.84                             ← 差异值（带正负号）
图：实线 = 当期，虚线 = 基准，两者叠加
```
> **这比只显示绝对值有信息量得多**，而且天然回答了"我这个月比上个月好还是差"。

**③ 侧边栏的账户分组**
```
All accounts   41,984.74    ← 总
On budget       8,897.74    ← 预算内
  Bank of America  3,095.67
  Ally Savings     5,450.31
  …
Off budget     33,087.00    ← 预算外
  Mortgage      -320,957.31
  …
+ Add account
```
> **"On budget / Off budget" 的分组**与我们的「豁免类目」概念相通 ——
> 它把账户分成"纳入预算"和"不纳入预算"两类。

**④ Transaction Calendar（与 ezBk 不同）**
```
并排 4 个月（7月 8月 9月 10月）
每格：日期 + 一根小柱状图（绿=净流入，红=净流出）
每月表头：↑4,386.25（绿） ↓755.98（红）  ← 月合计
```
> **按"净额"用柱状图表达**，比 ezBk 的"收入/支出两行文字"更紧凑。

**⑤ 色彩语义**
```
绿色 #0E9F6E 左右 = 正向（收入、净增）
红色 #D64545 左右 = 负向（支出、净减）
```
> 注意与国内习惯相反：**它这里是"绿涨红跌"**。
> MMH 已有 `colorScheme` cookie（`red_up_green_down`）支持两种约定，**沿用 MMH 现有设置**。

## 三、我们的设计决定（融合两者 + 叠加预算）

### 3.1 组件清单与来源

| 组件 | 抄谁 | 我们的改动 |
|---|---|---|
| **交易日历** | ezBookkeeping（日期+收支两行）| **每格加"当日预算剩余"或"当日可用额度"** ← 用户点名的创新 |
| **交易热力图** | ezBookkeeping（日×周橙色深浅）| **色深维度可选**：金额 / **预算消耗比**（P2 的 F23）|
| **KPI 大数字卡** | Actual（超大字号 + 小标签 + 时间范围）| 加"本月 vs 上月"的差异值 |
| **当期 vs 基准对比图** | Actual（实线 vs 虚线 + 副标题写明口径）| 用于**预算进度**：实线=本月消耗，虚线=时间进度线 |
| **支出分类排行** | ezBookkeeping（进度条 + 金额 + 占比）| 进度条改为**预算进度条**，超支变红 |
| **时间汇总卡**（今天/本周/本月/今年）| ezBookkeeping | 保留，加"预算剩余"一行 |

### 3.2 ⭐ 核心创新：把预算落到交易日历上

> ⚠️ **本小节是早期草案，已由 [第五章](#五-最终方案按-actual-的日历实现--预算融入已定稿) 取代。**
> 最终方案（颜色编码健康度、进度条基准线）见第五章。

这是用户明确要求的（「交易日历和热力图增加预算就更好了」）。
设计如下：

**每格显示三层信息**：
```
┌─────────────┐
│ 11          │  ← 日期
│ ↑6,000.00   │  ← 当日收入
│ ↓402.83     │  ← 当日支出
│ ─────────   │
│ 余 1,234.5  │  ← ⭐ 当日结束时，本月总预算的剩余
└─────────────┘
```

**配色规则**（沿用已定的三级）：
```
剩余 > 20% 额度   → 绿
剩余 0 ~ 20%      → 黄
剩余 < 0（超支）  → 红底
```

**另一个可选维度**：显示「当日可用额度」（剩余额度 ÷ 剩余天数），
让你每天知道"今天还能花多少"。这是 F21。

### 3.2.5 从截图直接对比出的「NEW vs OLD」

用户说 Firefly III / Actual 的交互「OLD」，而这两张截图**恰好展示了 NEW 的样子**。
把差异列清楚，作为实现的验收标准：

| 维度 | **NEW**（截图中）| **OLD**（用户否定的那种）|
|---|---|---|
| **信息载体** | 卡片 + 大数字 + 图表 | 密集表格 + 小字号字段堆叠 |
| **留白** | 卡片间大量呼吸空间 | 边距紧凑，元素贴边 |
| **数值表达** | KPI 用超大字号（30-48px）| 数值和标签同样大小 |
| **色彩** | 大面积白底 + 少量语义色点缀 | 到处是边框线、背景色块 |
| **层级** | 一眼看到"最重要的数" | 需要逐行阅读才能理解 |
| **图表** | 面积图/柱状/热力图/日历（视觉化）| 纯文字或简单表格 |
| **对比** | 当期 vs 基准叠加（实线/虚线）| 只有绝对值 |
| **编辑** | 弹层内完成，不离开页面 | 跳转到独立表单页 |
| **时间导航** | 卡片自带时间范围标注 | 靠顶部筛选器 |

> **关键洞察**：这两张截图都是「**先给结论，细节按需展开**」的结构 ——
> 顶部四张大数字卡片先告诉你"总共多少、平均多少"，
> 下面的图表才展开细节。**我们照这个顺序组织预算页**。

### 3.5 数据需求（已核实）

| 用途 | 现成能力 | 需要新写 |
|---|---|---|
| 本月收入/支出 | ✅ `computeOverviewSummary` 已有 `monthIncome`/`monthExpense` | — |
| 今天 / 本周 / 今年 | ❌ 无 | **新增聚合**（复用 `startOfDayUtc` / `addDaysUtc` / `addCalendarYearsUtc`）|
| 交易日历（按日收支）| ❌ `getIncomeExpenseReport` 只支持 `month`/`year` | **新增日粒度聚合** |
| 交易热力图（按日金额）| ❌ 同上 | **同上（可共用同一个日聚合）** |

**关键**：日历与热力图**共用同一个"按日聚合"查询**，只是渲染方式不同。
一次查询出 `Map<YYYY-MM-DD, {income, expense}>`，两个组件分别消费。

必须注意：
- 排除 `deletedAt != null`、`type=transfer`、`type=investment`
- 排除内部流转（复用 `isCreditCardTransfer` 等语义函数，与统计页同口径）
- 用 `date >= start AND date < end` 的半开区间，避免月初/月末差一天
- 走现有索引（`@@index([accountId, date])` 等）

## 四、实施时的注意事项

1. **空数据状态**要专门设计 —— ezBk 的热力图在 demo 里几乎全空，观感不好。
   我们应：无数据时显示引导文案，或收缩到有数据的范围。
2. **热力图性能** —— 一年 365 格 × N 年，必须走索引聚合，不能全表扫描。
3. **日历格子的信息密度** —— 一格里塞"日期+收入+支出+预算剩余"在小屏幕上会挤。
   方案：**默认显示日期+支出+剩余**，收入用 hover/点击展开。
4. **深色模式** —— 两个参考产品都有深色模式，MMH 也有主题系统，必须适配。
5. **移动端** —— 两个截图都是桌面版；ezBk 另有移动版布局。
   MMH 有 `MobileNavigation.tsx`，移动端要考虑降级（少放组件，纵向排列）。

## 五、⭐ 最终方案：按 Actual 的日历实现 + 预算融入（已定稿）

用户指示「参考 Actual 实现方案」。我读完了 Actual 的日历源码
（`packages/desktop-client/src/components/reports/spreadsheets/calendar-spreadsheet.ts`，267 行），
**结论如下**。

### 5.1 Actual 的真实实现（源码事实）

**数据结构**：
```ts
export type CalendarDataType = {
  date: Date;
  incomeValue: number;    // 当日收入
  expenseValue: number;   // 当日支出
  incomeSize: number;     // 笔数（源码里未被填充，恒为 0）
  expenseSize: number;
};
```

**聚合方式**：支出与收入**分两个查询**，各自 `groupBy(['date'])` + `$sum: '$amount'`，
再按 `amount < 0` / `amount > 0` 区分。

> ⚠️ **重要**：`groupBy(date)` **只会返回"有交易的那些日期"**，
> 没有交易的日期根本不在结果里 → **必须补零**。

**补零（月历网格）**：
```js
const firstDay = startOfMonth(month);
const beginDay = startOfWeek(firstDay, { weekStartsOn: firstDayOfWeekIdx ?? 0 });
let totalDays = differenceInDays(firstDay, beginDay) + getDaysInMonth(firstDay);
if (totalDays % 7 !== 0) totalDays += 7 - (totalDays % 7);   // 补齐整周
// 逐日填充；不属于本月的日子填 0
```

**柱长归一化 —— 关键细节**：
```js
// 分母是「本月的」支出合计，不是全部
const totalExpenseValue = 当月各日支出之和;
getBarLength = (value) => (Math.abs(value) / totalExpenseValue) * 100;
```
→ **按月归一化**，保证每个月内部柱子可比，且不同月份不会因为总额差异而失衡。

**Actual 的日历不涉及预算** —— 它只画"每天收/支多少"，
预算在另一套 envelope 体系里按月管。

### 5.2 我们的方案（照 Actual + 融入预算）

**照抄的部分**（数据层与网格）：
- 按日聚合，返回 `Map<YYYY-MM-DD, {income, expense}>`
- **必须补零**（否则空日期丢失）
- 月历网格用 `weekStartsOn` + 补齐整周
- 柱长**按月归一化**

**预算的融入点 = 颜色**（与 Actual 的机制**不冲突、是叠加**）：

| 编码通道 | 表达什么 | 是否受预算影响 |
|---|---|---|
| **柱高 / 数字** | 当天收/支**金额** | ❌ 不受影响（保持 Actual 原样）|
| **颜色** | **预算健康度** | ✅ 预算融入在这里 |

**颜色的判定（累计口径，不是单日）**：
```
截至当天的累计支出  vs  截至当天的基准额度
基准额度 = 本月总预算 × (已过天数 ÷ 本月天数)      ← 时间进度摊平

偏差 = 累计实际 − 基准
  ≤ 0            → 绿色（落后于预算，健康）
  0 ~ 20%        → 黄色（接近）
  > 20%          → 红色（超前）
```

> **为什么用累计而不是单日**：单日 ¥500 可能是正常聚餐，也可能是失控；
> 但"**到这天为止比基准多花了 20%**"是明确信号。
> 这也是 Actual 首页 `Compare 10月 to 9月` 那种**基准对比**思路。

**月度进度条（Actual 虚线基准的等价物）**：
```
已花 ¥6,234 / ¥8,000 (78%)   ████████████░░░░░░░░
时间进度 61%（10/11 已过）    ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈
                              ↑ 实线 > 虚线 = 花得比时间快
```

### 5.3 四个决策点（依 Actual 方案定稿）

| 编号 | 问题 | **决定** | 依据 |
|---|---|---|---|
| **E1** | 基准按什么算 | **总预算摊到每日**（`额度 × 已过天数/总天数`）| Actual 是**月度**体系；类目摊开会把格子塞满 |
| **E2** | 热力图默认维度 | **默认金额**（保持 Actual 原样），**可切"预算偏差"** | Actual 日历本身就是金额口径 |
| **E3** | 格子写不写剩余数字 | **不写**，颜色表达 | Actual 格子里只有日期+数字+柱，无预算数字 |
| **E4** | 日预算写进模型吗 | **不写**，全部派生 | 用户已确认；MMH 只做月度 |

### 5.4 格子最终形态

```
┌─────────────┐
│ 11          │  ← 日期（灰色小字）
│ ▂▅▇         │  ← 柱：当日支出（按月归一化）
│ 402.83      │  ← 金额（Actual 的 expenseValue）
│             │  ← 背景/柱色 = 预算健康度（无预算时用中性色）
└─────────────┘
```

**无预算时的降级**：颜色退回中性（不用红绿），
即完全等同于 Actual 的原始日历 —— **保证零配置可用**。

## 六、讨论过程：预算融入日历与热力图的三种模式

用户指出：**参考 Actual，可以把预算融入交易热力图、交易日历中**。

### 6.0 Actual 真正值得学的不是布局，是「对比基准」这个编码方式

它首页三张卡（`This Month` / `Budget Overview` / `3-Month Average`）都是同一结构：

```
副标题：Compare 10月 2026 to 9月 2026      ← 写明对比口径
右上角：-158.84                             ← 差异值
图形：  实线 = 当期，虚线 = 基准            ← 两条线叠在一起
```

**关键洞察**：一张图里同时有**实际**和**应该**，才能一眼判断"快了还是慢了"。
日历如果只显示"当天花了多少"，用户仍要自己去心算月度和进度；
**把基准摊进每一天，判断就变成瞬时的**。

### 6.1 三种可选模式

#### 模式 A：每日热度（不融入预算，作为基线）

```
格子背景深浅 = 当天支出金额（相对本月最大值归一化）
格子内文字   = 日期 + 支出
```

- ✅ 实现最简单，纯历史回溯
- ❌ 看不出预算快慢

#### 模式 B：把预算摊成"日基准线"（**推荐**）

核心公式（不改数据模型，全是派生值）：

```
本月额度            = 总预算 amount
日均基准            = 本月额度 ÷ 本月总天数
到当天为止的基准    = 日均基准 × 已过天数
到当天为止的实际    = 月初到当天累计支出
偏差               = 实际 − 基准      → 正数=超前(危险)，负数=落后(健康)
每日可用            = (额度 − 已花累计) ÷ 剩余天数
```

**视觉表达**：格子内除了金额，用**一条细进度条**表达当日累计偏差：

```
┌──────────────┐
│ 11           │  ← 日期
│ ↓402.83      │  ← 当日支出
│ ▓▓▓░░░░░░░   │  ← 累计偏差条（超过半程变黄，到底变红）
└──────────────┘
```

- ✅ **零配置也有用** —— 没设预算时不显示进度条，设了才出现
- ✅ 判断瞬时化：绿=落后于基准、黄=接近、红=超前
- ✅ 完全复用已定的三级配色（80%/100%）
- ⚠️ 需要"总预算"或"类目预算"存在

#### 模式 C：日历格子按类目分解（信息密度最高）

```
┌──────────────┐
│ 11           │
│ 餐饮 ↓120    │  ← 每类一行 + 该类当日预算状态点
│ 日用 ↓82  ●  │  ← ● = 该类目预算状态色
│ 交通 ↓200    │
└──────────────┘
```

- ✅ 能定位"是哪个类目在超"
- ❌ **一格里塞太多**，小屏幕直接崩（MMH 有移动端）
- ❌ 用户真实数据里 22% 未分类 → 分解不完整

### 6.2 热力图的预算融入方式

**推荐「一个热力图 + 可切换的色深维度」**，而不是并排两个热力图：

| 色深维度 | 含义 | 用途 |
|---|---|---|
| **金额**（默认）| 当天花了多少钱 | 看消费集中度、找大额日 |
| **预算偏差** | 截至当天，实际 vs 基准的超前/落后 | 看整个月是否失控 |

理由：
- 两个热力图并排会让页面很重（用户刚说过 Actual「其他交互 OLD」，不能靠堆组件）
- 切换维度是**现代做法**（一个控件，两种视图），也是 ezBk 的做法
- 默认「金额」保证**没设预算时也能用**

### 6.3 月度进度条（呼应 Actual 的对比图）

在日历上方放一条**"实线 vs 虚线"的等价物**：

```
本月预算进度
  ████████████░░░░░░░░  已花 ¥6,234 / ¥8,000 (78%)
  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈   时间进度 61%（10/11 已过）
                        ↑ 实线高于虚线 = 花得比时间快
```

**这条"时间进度虚线"就是 Actual 虚线基准在预算场景的等价物**，
一句话说清"我是不是花太快了"。

### 6.4 三种模式的取舍与建议

| 维度 | 模式 A | **模式 B（推荐）** | 模式 C |
|---|---|---|---|
| 实现复杂度 | 低 | 中 | 高 |
| 是否融入预算 | ❌ | ✅ | ✅ |
| 零配置可用 | ✅ | ✅（自动降级为 A）| ❌ |
| 移动端可行 | ✅ | ✅ | ❌ |
| 能定位超支类目 | ❌ | ⚠️ 需下钻 | ✅ |
| 数据模型改动 | 无 | 无 | 无 |

**建议：模式 B 为主，配合 6.2 的热力图维度切换 + 6.3 的进度条对比。**
模式 C 作为 P2 的「点击某天展开当日明细」实现，不塞进格子。
