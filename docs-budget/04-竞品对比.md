## 一、结论速览

| 产品 | 技术栈 | 部署 | **预算功能** | 自托管 | 对我们的价值 |
|---|---|---|---|---|---|
| **ezBookkeeping** | Go + Vue | Docker/二进制，镜像仅 **57 MiB** | ❌ **明确不支持** | ✅ | **反面教材**：功能很全但没预算 |
| **Firefly III** | PHP + Laravel | Docker，镜像 **795 MiB** | ✅ 支持（周期 + 可结转）| ✅ | **正面参考**：预算周期与结转 |
| **Actual Budget** | TypeScript + React | Docker，镜像 **188 MiB** | ✅ 强（信封式）| ✅ | **理念参考**：透支与结转的处理 |
| **MMH（我们的）** | Next.js + Prisma | Docker（NAS）| ❌ 无 → **本次要加** | ✅ | 有最全的资产/投资/信用卡能力 |

**关键发现**：用户让分析的 **ezBookkeeping 明确没有预算功能** ——
它自己的功能对比表里写着「预算功能 ❌ 不支持」。
所以它**不能作为预算设计的主要参考**，真正该看的是 Firefly III 和 Actual Budget。

## 二、ezBookkeeping（用户指定分析）

**项目**：[mayswind/ezbookkeeping](https://github.com/mayswind/ezbookkeeping) · 官网 [ezbookkeeping.mayswind.net](https://ezbookkeeping.mayswind.net/zh_Hans/)
MIT 协议 · 作者 MaysWind · 活跃维护（功能表已列到 v2.1.0）

### 2.1 基本情况

```
语言/栈：Golang（服务端）+ Vue.js（前端）
部署：   Docker / 二进制 / Kubernetes / 1Panel
数据库： SQLite、MySQL、PostgreSQL  ← 三选一
体积：   镜像 57.7 MiB（amd64）· 启动 <1s（树莓派 4）
架构：   x86 / amd64 / ARM
```

### 2.2 ⚠️ 预算功能：**明确不支持**

**证据**（来自它自己的[功能对比页](https://ezbookkeeping.mayswind.net/zh_Hans/comparison/)，对比时间 2026 年 1 月）：

> **预算功能**
> | 项目 | ezBookkeeping | Firefly III | Actual Budget |
> |---|---|---|---|
> | 预算功能 | ❌ 不支持 | ✅ 支持 | ✅ 支持 |

我另外核对了它的完整[功能列表页](https://ezbookkeeping.mayswind.net/zh_Hans/features/)，
**全部 20 个分类里没有任何「预算」条目**，也没有「超支/提醒/警告/额度/限额」相关功能。

### 2.3 ezBookkeeping 里**最值得抄**的一个组件（源码级发现）

它虽然没有独立的"预算"模块，但总览页有一个小组件
**`MonthlyExpenseProgressWidget.vue`**（78 行，我读了全文），机制如下：

```
当前月支出额              ← 实时显示
本月已过 %  = 当前日 / 本月总天数        → 进度条
预计月末支出 = 当前支出 ÷ 已过比例        ← **线性外推预测**
上月总额                  ← 对照基准
```

核心代码：

```ts
const currentMonthElapsedPercent =
  currentDateTime.getGregorianCalendarDay() / currentDateTime.getMaxDayOfGregorianCalendarMonth();
const estimatedExpense = currentExpenseAmount.divide(currentMonthElapsedPercent);
const lastMonthExpense = transactionOverview.lastMonth?.expenseAmount ?? ZERO;
```

**为什么这个设计很有价值**：

| 优点 | 说明 |
|---|---|
| **零配置** | 不需要用户设任何额度，打开就有 |
| **趋势预警** | 额度预算是"事后超了才说"，这个能**提前**告诉你"照这速度月底要花 X" |
| **自动校准** | 用上月实际值作对照基准 |
| **实现极简** | 一个除法 + 一个进度条 |

**→ 建议纳入我们的 P1**（不是 P2）：
在预算页顶部同时显示「本月已过 X%」与「预计月末支出」，
**即使没设任何预算也有用**，而且直接复用我们已有的 `/statistics` 月度聚合。

**还学到一点架构**：它把统计类组件抽到
`src/views/base/overview/PeriodStatisticsWidgetBase.ts` 复用，
所以十几个总览组件都很薄。我们的 `BudgetList` / `BudgetAlertBanner`
也应共用同一个聚合 hook，避免各自查库。

其他可用组件（同为总览小组件，可作 UI 参考）：
`ExpenseCategoryRankingWidget.vue`（类目排行）、
`MonthlyExpenseOverviewWidget.vue`、
`PeriodNetIncomeAndSavingsRateWidget.vue`（储蓄率）。

### 2.4 它最强的地方（**不是**预算）

| 能力 | 详情 |
|---|---|
| **导入格式极全** | CSV/Excel/OFX/QFX/QIF/IIF/Camt.052/Camt.053/MT940/GnuCash/Firefly III/Beancount/随手记 + **支付宝/微信支付/京东金融对账单** |
| **洞察探索** | 高级查询 + **25 种图表**（桑基图/旭日图/日历热力图/矩形树图…）+ **90+ 统计指标**（基尼系数、赫芬达尔指数、偏度、峰度、四分位距…） |
| **AI 集成很前沿** | 内置 **MCP**（Model Context Protocol）、Agent Skill、AI 识图、AI 剪贴板识别、**AI 自定义图表代码生成** |
| **LLM 兼容广** | OpenAI / OpenAI 兼容 / Anthropic / Ollama / LM Studio / Google AI |
| **对象存储** | 本地 / S3 / MinIO / WebDAV |
| **安全** | 2FA / OIDC / Nextcloud / Gitea / GitHub 登录 / PIN / WebAuthn |
| **多币种** | 20 家央行汇率源 + 自定义 |

### 2.5 其他值得借鉴（与预算无关但有用）

1. **AI 自定义图表代码生成**（≥2.1.0）—— 让 LLM 生成图表脚本，
   而不是硬编码图表类型。**我们的"自然语言问答"可以走这个思路**：
   让 LLM 产出查询计划，而不是直接产出答案。
2. **MCP 内置支持** —— 它把自己暴露成 MCP server，任何 AI 客户端都能读写。
   **这比我们目前的"面板层手动适配"更通用**，值得考虑。
3. **极致的导入格式覆盖** —— 尤其**直接支持微信/支付宝/京东账单**。
   我们目前是自己写解析器（招商银行 PDF 那个坑），可以参考它的清单。
4. **「洞察探索」的指标库** —— 90+ 统计指标是可复用的设计清单，
   我们做"消费异常检测"时可以直接挑（如基尼系数衡量消费集中度）。

### 2.6 对我们决策的影响

**ezBookkeeping 直接出局**作为预算方案的候选——
它没有预算功能，而「预算 + 超支警告」正是用户的核心诉求。

> 反过来说，这**验证了 fork MMH 的合理性**：
> 一个功能这么全、维护这么活跃的项目都没有预算，
> 说明「在成熟记账系统上加预算」是一个真实且未被满足的需求。

## 三、Firefly III（真正的预算对标）

**项目**：firefly-iii/firefly-iii · PHP + Laravel · Docker 镜像 795 MiB
**文档**：[docs.firefly-iii.org](https://docs.firefly-iii.org/how-to/firefly-iii/finances/budgets/)
（注：官网被 Cloudflare 拦截，我未能抓取全文，以下基于搜索摘要与公开信息，**标注为待核实**）

### 3.1 预算模型（待核实细节）

- **预算绑定到「预算（Budget）」实体**，交易可关联多个预算
- **支持预算周期（budget ranges / period）**：月度、季度、年度、自定义区间
- **支持结转（rollover）**：未用完的额度可带到下期
  - 社区讨论：[Tracking Month to Month Budget Surplus #11761](https://github.com/orgs/firefly-iii/discussions/11761)
  - 已知缺陷：[Budget rollover not working due to date format in database #9646](https://github.com/firefly-iii/firefly-iii/issues/9646)
    → **说明结转是个容易出错的功能，我们 MVP 不做是对的**

### 3.2 对我们的启示

| 它的做法 | 我们的取舍 |
|---|---|
| 预算有独立的 period（月/季/年） | MVP **只做月度**（决策 D1）|
| 支持结转 | **不做**，且看到它有 bug 更坚定 |
| 交易可关联多个预算 | 我们的 `categoryId` 一对一，**更简单但够用** |
| 镜像 795 MiB | MMH 走 Next.js standalone，量级不同，不比较 |

## 四、Actual Budget（预算理念最强）

**项目**：actualbudget/actual · TypeScript + React · Docker 镜像 188 MiB · 有 API
**文档**：[How Budgeting Works](https://actualbudget.org/docs/budgeting/)

### 4.1 核心机制：信封式（Envelope Budgeting）

原文要点（已抓取全文）：

> Instead of predicting how much you'll make and spend and trying to reconcile that
> with what actually happened, envelope budgeting embraces **real income as the
> source of your budget**. This means you can **only budget money that you already have**.

三条关键规则：

1. **零基**：把账户余额分配完，「To budget」归 0
2. **结转（rollover）**：
   - 收入未分配 → 自动滚到下月
   - **透支自动从下月「To budget」扣**，类目余额清零
   - 类目有剩余 → 滚入下月该类目余额
3. **资金可在类目间转移**（Transfer to another category）

### 4.2 ⚠️ 为什么不照抄它

| 它的要求 | 我们账本的现实 |
|---|---|
| **所有收入必须分配完** | 我们 2026 年收入 ¥857,701，用户不会去逐个分配 |
| **所有支出必须有类目** | 我们 **410 笔 ¥191,989（22%）未分类** → 信封式直接崩 |
| **每月手工建新预算** | 用户要的是「设一次、自动盯」，不是每月手工操作 |
| 类目余额是核心概念 | 用户的诉求是「**别超支**」，不是「账目归零」 |

**核心差异**：Actual Budget 是**分配型**（把钱分到信封里），
MMH 需要的是**限额型**（给类目设上限 + 超了告诉我）。

> 这不是"谁更好"，而是**匹配度问题**。信封式对愿意投入精力的人是神器，
> 对"只想被提醒"的用户是负担。

### 4.3 值得借鉴的具体设计

1. **透支的显式处理** —— 它明确定义了「超支了怎么办」（从下月扣）。
   我们虽然不做结转，但**UI 上要说清"超支后下月会怎样"**，
   哪怕答案是"不影响，只是提醒"。
2. **类目间转移资金** —— 用户超支时，自然的动作是"从别处挪"。
   我们 P2 可以考虑「调高这个类目的额度」的快捷操作。
3. **「可用资金」置顶** —— 它把 To budget 放在最显眼位置。
   我们对应的是**总预算的剩余额度**，应该也置顶。

## 五、MX Budgets Widget（商业方案，我们已参考）

**来源**：[MX Budgets Widget 文档](https://docs.mx.com/products/experience/pfm/widget-overviews/budgets-widget)

MX 是美国主流金融科技方案商，这个组件被大量银行 App 采用。**我们已采纳它的核心设计**：

```
绿 = 用量 < 80%
黄 = 80% ~ 100%
红 = 超过 100%
```

其他可借鉴点：

- **自动生成预算**：按各品类**过去两个月平均支出**生成初始额度
  → 我们 **P2** 可做（复用现有 `/statistics` 的类目聚合）
- **气泡可视化**：大小 = 占收入比例，颜色 = 健康度
  → 比单纯的进度条信息量更大
- **主预算 + 子预算两级**，子预算调高自动抬高主预算
  → 我们的类目树本身是两级的（`Category.parentId`），**天然支持**

## 七、最终建议

### 7.1 设计上抄谁

| 抄什么 | 抄谁 | 理由 |
|---|---|---|
| **三级阈值配色（80/100）** | **MX** | 已被验证的商业方案，简单有效 |
| **自动生成额度（按历史均值）** | **MX** | P2 做，复用现有统计聚合 |
| **透支的显式说明** | **Actual Budget** | 用户必须知道"超了会怎样" |
| **「剩余可用」置顶** | **Actual Budget** | 最重要的数字放最显眼处 |
| **月度支出进度 + 预计月末支出** | **ezBookkeeping** | 零配置就有用；额度预算只能事后预警，这个能提前预测 |
| **预算周期概念** | **Firefly III** | 但 MVP 只做月度 |
| **结转** | ❌ 都不抄 | Firefly III 的结转有已知 bug，MVP 不做 |

### 7.2 明确不抄的

- ❌ **零基/信封式**（Actual Budget）—— 与用户账本现实（22% 未分类）不匹配
- ❌ **结转**（Firefly III / Actual）—— 复杂度高、易出错、非当前诉求
- ❌ **多周期**（Firefly III）—— MVP 只做月度

### 7.3 对 ezBookkeeping 的最终判断

**它不能作为预算功能的参考**（没有该功能），
但它的 **MCP 集成** 和 **AI 自定义图表** 两个思路，
对我们未来的「自然语言问答」方向有借鉴价值 —— **记入待办，不在本次范围**。

---

## 八、结论

1. **ezBookkeeping 没有预算功能** —— 它自己的对比表确认。用户让分析它，
   结果是「它做不了这件事」，这反而**强化了 fork MMH 加预算的决策**
2. **真正的对标是 Firefly III 和 Actual Budget**，但它们都是"重度预算"路线
   （周期/结转/零基），与用户"设限额 + 被提醒"的诉求**不是一回事**
3. **MMH 要做的是「限额型预算」而非「分配型预算」** —— 这是本次设计的核心定位，
   也决定了我们要**刻意不做**结转与零基
4. **最该抄的是 MX 的三级配色 + 自动额度**，外加 Actual Budget 的"透支说明"
